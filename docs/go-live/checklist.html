0How deploys work Done

So the steps below make sense, here is the pipeline that is already wired up.

Staging apphttps://ent.stage.heyvacay.co (live now)

Every integration below follows the same pattern: the app already calls the live API when its secret is present, and falls back to realistic demo data when it isn't. So "turning it on" always means the same three moves — (a) store the key in AWS Secrets Manager, (b) reference it in ent.tf, (c) redeploy. No code changes needed.

1Ship everything to production Action needed

Promote the completed work so it is live on the real domain.

  1. Open the pull request.
    • Go to github.com/heyvacay/heyvacay-ent → Pull requests → New pull request.
    • Base = stage, compare = claude/real-search. Click Create pull request, then Merge.
    • The merge auto-runs the deploy workflow. Watch it under the Actions tab → Stage Web Enterprise - Deploy.
  2. Verify staging. When the workflow is green, open https://ent.stage.heyvacay.co and spot-check sign-in, a booking, and Nova.
  3. Promote to production (once a prod environment/branch exists — e.g. main → ent.heyvacay.co). Repeat the merge into the production branch. If production infra isn't stood up yet, see step 8 (DNS).

2Payments — Stripe (same processor as heyvacay.co) Action needed

The checkout already initializes payment through the shared HeyVacay backend and the same tracking tags. You only need to make sure the keys are present.

Where: AWS Secrets Manager → then heyvacay-iac → then redeploy.
  1. Get the exact keys heyvacay.co uses. In the Stripe Dashboard (dashboard.stripe.com) → Developers → API keys, copy the same live Secret key (sk_live_…) and Publishable key (pk_live_…) that heyvacay.co runs on. (Same Stripe account = same processor, same payout, same reporting.)
  2. Store them as secrets. AWS Console → Secrets Manager (us-west-2) → Store a new secret → Other type of secret → add key/value pairs:
    • STRIPE_SECRET_KEY = your sk_live_…
    • STRIPE_PUBLISHABLE_KEY = your pk_live_…
    Name it e.g. stage/heyvacay-ent/stripe and save. Copy the resulting secret ARN.
  3. Reference them on the container. In heyvacay-iac → ent.tf, add to the task definition's secrets block (one entry per key), pointing valueFrom at the secret ARN + JSON key. Run terraform apply.
  4. Confirm the payment-tracking endpoint. The app POSTs to {ENT_API_BASE_URL}/bookings/payment/init-stripe with metadata tags source: heyvacay-enterprise, product: corporate-travel. Make sure ENT_API_BASE_URL points at the same backend heyvacay.co uses so charges land in the same ledger. (Defaults to https://api.stage.heyvacay.co.)
  5. Redeploy & test (step 1). Do a $1 test booking; confirm it appears in the Stripe Dashboard → Payments with the metadata tags, then refund it.
Already done for you: the full Stripe Elements checkout, saved-card option, the booking + booking-confirmed screens matched to heyvacay.co (including the confetti), and the metadata tags. Without keys, checkout stays in clearly-labelled DEMO MODE — no real charge.

3Dining — OpenTable API Action needed

Powers the restaurant directory, availability and reservations used by the Events dinner flow.

Where: OpenTable for Partners → AWS Secrets Manager → heyvacay-iac → redeploy.
  1. Request API access. Go to https://platform.opentable.com (OpenTable Partner / Affiliate program). Sign in with the HeyVacay OpenTable partner account, or click Become a partner and complete the application for API access.
  2. Create an app / credentials. In the partner portal → Apps (or Credentials) → Create app. OpenTable will issue either a single API key or an OAuth Client ID + Client Secret.
  3. Note the base URL. Default is https://platform.opentable.com. If your partner docs specify a different host, keep it handy for OPENTABLE_API_BASE.
  4. Store the secret(s) in Secrets Manager (as in step 2), using whichever you were issued:
    • OPENTABLE_API_KEY, or
    • OPENTABLE_CLIENT_ID + OPENTABLE_CLIENT_SECRET
    • (optional) OPENTABLE_API_BASE if non-default
  5. Reference in ent.tf → terraform apply → redeploy (step 1).
  6. Verify. Open the app → Events → dinner flow; live restaurants and times should now appear instead of demo data.
Already done: the full dining UI, search, RSVP and dinner-invite emails. The moment the key is present the same screens call OpenTable live.

4Transactional email Action needed

Sends approval requests, offers, event-added notices, dinner invites, and the C-Suite commission alerts.

Where: your email provider → Secrets Manager → heyvacay-iac → redeploy.
  1. Pick/confirm the provider heyvacay.co uses (e.g. SendGrid, Postmark, or AWS SES). Log in and create an API key with send permission.
  2. Verify the sender domain in the provider so mail from notifications@heyvacay.co passes SPF/DKIM. (For SES: Verified identities → add domain → publish the DNS records it gives you.)
  3. Store secrets: EMAIL_API_KEY = the key; EMAIL_FROM = notifications@heyvacay.co (or your preferred from-address).
  4. Reference in ent.tf → terraform apply → redeploy.
  5. Verify. Submit a trip for approval; the approver should receive a branded email. Also confirm a C-Suite commission-limit alert sends when a rep exceeds the ±band.

5Live trip data — Weather & Flight status Action needed

Optional polish for the active-trip view. Everything works without them (demo data); add keys to go live.

Weather (OpenWeather)
  1. Create a free key at https://openweathermap.org/api → Sign up → API keys.
  2. Store WEATHER_API_KEY in Secrets Manager (base defaults to OpenWeather; override with WEATHER_API_BASE if needed).
  3. Reference in ent.tf → apply → redeploy.
Flight status
  1. Choose a provider (e.g. AviationStack aviationstack.com, or FlightAware AeroAPI). Sign up and copy the API key + its base URL.
  2. Store both: FLIGHT_STATUS_API_KEY and FLIGHT_STATUS_API_BASE (both are required for it to go live).
  3. Reference in ent.tf → apply → redeploy.

6DNS, login screens & domain self-join Action needed

The login screens are built and waiting; they go live the moment DNS points at the app.

Where: your DNS provider (Route 53 / registrar) + heyvacay-iac.
  1. Production subdomain. In Route 53 (or your DNS host) create an A / ALIAS record for ent.heyvacay.co pointing at the Enterprise load balancer (ALB) created by heyvacay-iac. Add it to the ALB listener + ACM certificate (SAN) so HTTPS is valid.
  2. Internal Nova subdomain (optional). Point ent.nova.heyvacay.co at the same service if you want the internal console on its own host; otherwise it stays at /nova on the app.
  3. Login screens — already built at /signin (SSO buttons, work-email, and a domain-join hint) and /signup. No action beyond DNS; they render on the new domain automatically.
  4. Domain self-join backend. The UI is done: on each company profile (Sales → Companies → a company → Domain self-join) you register the company's email domain and toggle auto-join. To make it enforce for real, the auth backend must, on email verification: match the verified domain to a company with self-join enabled and create the user at the lowest (traveler) role. Hand this spec to the backend team — the enterprise app reads the flag and surfaces the hint today.
  5. Verify. Hit https://ent.heyvacay.co/signin, type a corporate-domain email, and confirm the "you'll be added automatically once verified" hint appears.
